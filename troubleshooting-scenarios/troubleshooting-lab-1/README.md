# 네트워크 장애 진단 및 복구 실습

Router-on-a-Stick과 OSPF 환경에서 의도적으로 설정 오류와 인터페이스 장애를 발생시키고, 원인 분석 및 복구 과정을 기록했습니다.

---

## 🔎 1단계 — 잘못된 기본 게이트웨이 설정

VLAN 10 호스트의 **Layer 3 설정**을 의도적으로 변경하여 VLAN 간 통신 장애를 발생시켰습니다.

R1의 Router-on-a-Stick 설정은 정상이었지만, 호스트의 기본 게이트웨이가 잘못되어 VLAN 20에 접근하지 못했습니다.

### 🎯 목표

- 잘못된 기본 게이트웨이가 VLAN 간 통신에 미치는 영향 확인
- ARP 동작과 ICMP 통신 실패 과정 관찰
- 게이트웨이 수정 후 정상 라우팅 복구 확인

### 🧪 테스트 환경

#### VLAN 10 호스트

- IP 주소: `192.168.10.x`
- 서브넷 마스크: `255.255.255.0`
- 잘못 설정한 기본 게이트웨이: `192.168.10.15`
- 올바른 기본 게이트웨이: `192.168.10.1`

#### R1의 Router-on-a-Stick 구성

| 서브인터페이스 | IP 주소 |
|---|---|
| Gig0/0/0.10 | 192.168.10.1 |
| Gig0/0/0.20 | 192.168.20.1 |
| Gig0/0/0.30 | 192.168.30.1 |

#### 테스트

VLAN 10 호스트에서 VLAN 20 호스트 `192.168.20.x`로 ping을 실행했습니다.

### 🔍 관찰 결과

❌ **VLAN 10 → VLAN 20 ping 실패**

실패 과정은 다음과 같습니다.

1. 호스트가 기본 게이트웨이로 설정된 `192.168.10.15`의 MAC 주소를 알아내기 위해 ARP 요청을 전송했습니다.
2. 해당 주소를 사용하는 장비가 없어 응답을 받지 못했습니다.
3. 게이트웨이의 MAC 주소를 확인하지 못했습니다.
4. ICMP Echo Request가 R1까지 전달되지 못했습니다.
5. VLAN 간 라우팅이 수행되지 않았습니다.

이 실습에서는 호스트의 기본 게이트웨이 설정 오류가 장애 원인이었습니다.

### 🛠️ 해결 방법

기본 게이트웨이를 다음 주소로 수정했습니다.

```text
192.168.10.1
```

수정 후 다음 동작을 확인했습니다.

- 정상 게이트웨이에 대한 ARP 응답 수신
- ICMP Echo Request가 R1의 Gig0/0/0.10에 도달
- R1이 패킷을 VLAN 20으로 라우팅
- 응답 패킷이 VLAN 10 호스트로 정상 전달

✅ **Ping 성공**

### 📌 핵심 교훈

원격 네트워크 통신 장애가 발생하면 호스트의 기본 설정부터 확인해야 합니다.

- IP 주소
- 서브넷 마스크
- 기본 게이트웨이

## 🔎 2단계 — 액세스 포트의 잘못된 VLAN 할당

호스트의 IP 주소, 서브넷 마스크, 기본 게이트웨이는 유지한 채, 연결된 스위치 포트를 잘못된 VLAN에 할당했습니다.

이를 통해 **Layer 2의 VLAN 소속 오류**가 VLAN 간 통신에 미치는 영향을 확인했습니다.

### 🎯 목표

다음 설정이 정상이더라도 액세스 포트의 VLAN이 잘못되면 통신이 실패할 수 있음을 확인합니다.

- 호스트 IP 주소
- 서브넷 마스크
- 기본 게이트웨이
- 라우터 서브인터페이스

### 🧪 테스트 환경

#### 호스트가 속해야 하는 VLAN: VLAN 10

- IP 주소: `192.168.10.x`
- 서브넷 마스크: `255.255.255.0`
- 기본 게이트웨이: `192.168.10.1`

#### 의도적으로 적용한 잘못된 설정

```cisco
interface Fa0/1
 switchport mode access
 ! 잘못된 VLAN 할당
 switchport access vlan 30
```

#### R1 서브인터페이스

| 서브인터페이스 | IP 주소 |
|---|---|
| Gig0/0/0.10 | 192.168.10.1 |
| Gig0/0/0.20 | 192.168.20.1 |
| Gig0/0/0.30 | 192.168.30.1 |

### 🔍 관찰 결과

- ❌ VLAN 10용 IP 설정을 가진 테스트 호스트에서 VLAN 20으로 ping 실패
- ✅ 정상적으로 구성된 VLAN 30 호스트에서는 VLAN 20으로 ping 성공

시뮬레이션에서는 일부 ICMP Echo Request가 목적지에 도달한 것으로 관찰되었지만, ping은 실패했습니다.

### 🧬 원인 분석

호스트는 VLAN 10의 IP 주소를 사용하고 있었지만, 실제 연결 포트는 **VLAN 30**에 속해 있었습니다.

따라서 호스트의 IP 서브넷과 실제 Layer 2 브로드캐스트 도메인이 일치하지 않았습니다.

일반적으로 이 상태에서는 다음 문제가 발생할 수 있습니다.

- 기본 게이트웨이 `192.168.10.1`에 대한 ARP 요청이 VLAN 30으로 전달됨
- VLAN 10의 게이트웨이에 ARP 요청이 도달하지 못함
- 게이트웨이 MAC 주소를 확인하지 못하여 통신 실패

기존 ARP 캐시나 장비 동작에 따라 요청이 전달되더라도, R1의 응답 경로는 `192.168.10.0/24`가 연결된 VLAN 10을 향하므로 잘못 배치된 호스트까지 응답이 도달하지 못할 수 있습니다.

> 잘못된 VLAN 할당이 항상 단방향 통신을 만드는 것은 아닙니다. ARP 캐시와 실제 패킷 흐름을 함께 확인해야 합니다. 액세스 포트의 호스트 프레임은 일반적으로 태그가 없으며, 스위치가 해당 포트의 VLAN에 분류합니다.

### 🛠️ 해결 방법

호스트 연결 포트의 VLAN을 수정했습니다.

```cisco
interface Fa0/1
 switchport access vlan 10
```

수정 후 다음을 확인했습니다.

- 호스트가 올바른 VLAN에 배치됨
- 기본 게이트웨이에 대한 ARP 정상 동작
- 요청 및 응답 패킷의 정상 전달
- VLAN 간 ping 성공

### 📌 핵심 교훈

호스트의 IP 설정이 정상이어도 액세스 포트의 VLAN 소속이 잘못되면 통신이 실패할 수 있습니다.

VLAN 간 통신 장애를 진단할 때는 초기에 다음 항목을 확인해야 합니다.

- 액세스 포트의 VLAN 소속
- 게이트웨이에 대한 ARP 상태
- 트렁크의 VLAN 전달 상태
- 라우터 서브인터페이스의 VLAN ID

## 🔎 3단계 — OSPF 설정 누락: VLAN 20 경로 미광고

R1의 VLAN, 서브인터페이스 및 로컬 라우팅은 정상인 상태에서, VLAN 20 인터페이스가 OSPF에 포함되지 않도록 설정했습니다.

그 결과 R2와 R3이 VLAN 20 경로를 학습하지 못하는 **부분적인 도달성 장애**가 발생했습니다.

### 🎯 목표

- R2와 R3에서 특정 네트워크의 경로 누락 확인
- 일부 목적지에만 발생하는 ping 실패 분석
- OSPF 인접 관계와 경로 광고 상태를 구분하여 확인
- 설정, LSDB, 라우팅 테이블을 연계한 진단 수행

### 🧪 네트워크 구성

모든 라우터는 OSPF Area 0을 사용합니다.

#### R1의 VLAN 게이트웨이

- `192.168.10.1`
- `192.168.20.1`
- `192.168.30.1`

#### 라우터 간 링크

| 구간 | 네트워크 |
|---|---|
| R1–R2 | 10.0.0.4/30 |
| R2–R3 | 10.0.0.0/30 |

### 🚫 의도적으로 누락한 설정

R1에서 VLAN 20에 해당하는 network 명령어를 제외했습니다.

```cisco
router ospf 1
 network 192.168.10.0 0.0.0.255 area 0
 ! 누락한 설정:
 ! network 192.168.20.0 0.0.0.255 area 0
 network 192.168.30.0 0.0.0.255 area 0
 network 10.0.0.4 0.0.0.3 area 0
```

이 실습에서는 VLAN 20에 대한 별도의 인터페이스 단위 OSPF 설정이나 연결 경로 재분배를 사용하지 않았습니다.

### 🔍 관찰 결과

R2 및 R3에서 다음 결과를 확인했습니다.

- ✅ `192.168.10.1`로 ping 성공
- ✅ `192.168.30.1`로 ping 성공
- ❌ `192.168.20.1`로 ping 실패

라우팅 테이블에서도 VLAN 20 경로가 없었습니다.

```text
R2# show ip route 192.168.20.0
% Network not in table
```

OSPF 인접 관계는 유지되었지만 VLAN 20 경로는 학습되지 않았습니다.

### 🧬 원인 분석

OSPF는 모든 연결 네트워크를 자동으로 광고하지 않습니다.

이 구성에서 network 명령어는 일치하는 IP 주소를 가진 인터페이스에 OSPF를 활성화하고 Area를 지정합니다.

VLAN 20 인터페이스가 OSPF에 포함되지 않았으므로 다음 결과가 발생했습니다.

- R1의 OSPF 광고에 `192.168.20.0/24` 정보가 포함되지 않음
- R2와 R3이 해당 경로를 학습하지 못함
- 대체 경로가 없는 상태에서 VLAN 20으로의 통신 실패

R1에는 VLAN 20의 연결 경로가 있으므로 로컬 VLAN 간 라우팅은 정상적으로 동작했습니다.

### 🛠️ 해결 방법

R1의 OSPF 설정 모드에서 다음 명령어를 추가했습니다.

```cisco
network 192.168.20.0 0.0.0.255 area 0
```

OSPF 수렴 후 다음을 확인했습니다.

- R2와 R3이 VLAN 20 경로 학습
- 라우팅 테이블에 해당 경로 설치
- `192.168.20.1`로 ping 성공

OSPF 인접 관계가 정상이어도 필요한 네트워크가 모두 광고되고 있다는 뜻은 아닙니다.

일부 목적지에만 접근할 수 없다면 다음 항목을 확인해야 합니다.

- running-config
- OSPF 활성 인터페이스
- 링크 상태 데이터베이스(LSDB)
- OSPF 학습 경로

## 🔎 4단계 — R1의 상위 물리 인터페이스 종료

R1의 Router-on-a-Stick 상위 물리 인터페이스인 **Gig0/0/0**을 종료했습니다.

R2와의 OSPF 인접 관계는 별도 인터페이스인 **Gig0/0/1**을 사용하므로 유지되었습니다.

이를 통해 라우터 간 OSPF 연결은 정상이지만, R1의 VLAN 게이트웨이가 모두 동작하지 않는 상황을 확인했습니다.

### 🎯 목표

- 상위 물리 인터페이스 종료에 따른 서브인터페이스 상태 변화 확인
- OSPF 광고 내용의 갱신 확인
- R2 및 R3에서 VLAN 경로가 제거되는 과정 확인
- OSPF 인접 관계가 유지되는 상태에서 게이트웨이 통신 실패 확인

### 🧪 테스트 환경

#### R1의 Router-on-a-Stick 구성

| 서브인터페이스 | 게이트웨이 IP |
|---|---|
| Gig0/0/0.10 | 192.168.10.1 |
| Gig0/0/0.20 | 192.168.20.1 |
| Gig0/0/0.30 | 192.168.30.1 |

#### R1–R2 OSPF 연결

- R1 인터페이스: `Gig0/0/1`
- 네트워크: `10.0.0.4/30`

### 🚫 의도적으로 발생시킨 장애

R1에서 상위 물리 인터페이스를 종료했습니다.

```cisco
interface Gig0/0/0
 shutdown
```

이로 인해 해당 인터페이스에 속한 VLAN 서브인터페이스도 동작하지 않게 되었습니다.

### 🔍 관찰 결과

#### R3에서 게이트웨이 통신 실패

```text
ping 192.168.30.1
```

❌ Ping 실패

#### R2 및 R3의 라우팅 테이블

OSPF 수렴 후 VLAN 10, 20, 30의 경로가 제거되었습니다.

#### OSPF 인접 관계

R1–R2 인접 관계는 별도 링크를 사용하므로 **FULL 상태를 유지**했습니다.

### 🧬 원인 분석

1. Gig0/0/0 종료로 관련 서브인터페이스가 다운되었습니다.
2. 해당 VLAN의 연결 경로가 R1의 활성 라우팅 테이블에서 제거되었습니다.
3. R1이 OSPF 광고 내용을 갱신했습니다.
4. R2와 R3이 경로를 다시 계산하여 해당 VLAN 경로를 제거했습니다.
5. 대체 경로가 없는 상태에서 VLAN 게이트웨이로의 통신이 실패했습니다.

> 서브인터페이스의 IP 설정 자체가 삭제된 것은 아닙니다. 인터페이스가 다운되어 해당 연결 경로와 게이트웨이를 사용할 수 없게 된 것입니다.

### 🛠️ 해결 방법

상위 물리 인터페이스를 다시 활성화했습니다.

```cisco
interface Gig0/0/0
 no shutdown
```

링크 복구 및 OSPF 수렴 후 다음을 확인했습니다.

- VLAN 서브인터페이스의 정상 동작 복구
- R1의 VLAN 네트워크 재광고
- R2 및 R3의 경로 재설치
- 게이트웨이로의 ping 성공
